## 3-1 지표 정의와 누락값

**상황:** 평균 응답 시간이 빨라졌는데, 사실은 느린 요청이 실패해서 완료 목록에서 빠진 것일 수 있다.

- 지표는 품질 · 지연 · 오류율 · 토큰/비용 네 가지이고, 하나를 개선하면 다른 것이 나빠질 수 있다.
- **SLI** = 실제로 측정하는 지표 (예: 완료 요청의 p95 지연), **SLO** = 일정 기간 지키기로 한 목표. 목표를 정하려면 요청 범위 · 측정 구간 · 기간을 같이 정의한다.
- (참고) SLA = 고객과의 약속. 어기면 보상이 따르고 보통 SLO보다 느슨하다.

**같은 5건도 지표마다 분모가 다르다**

| 요청 | 상태 | 지연 ms | 비용 $ |
| --- | --- | --- | --- |
| A | completed | 100 | 0.001 |
| B | completed | 200 | 0.002 |
| C | completed | 900 | None |
| D | failed | 300 | 0.001 |
| E | unknown | None | None |

| 지표 | 포함되는 행 |
| --- | --- |
| 오류율 | A B C D E (5건) |
| 완료 지연 | A B C (3건) |
| 알려진 비용 | A B D (3건) |

- 완료 3건과 비용 3건은 숫자만 같은 **다른 집합**이다.
- D는 실패했는데 비용이 있다 → 완료 요청만 골라 비용을 더하면 과소 집계된다. 비용은 상태로 거르지 않는다.

**완료 · 실패 · 미확인을 나눈다**

- 완료 3/5 = 60%, 명시적 실패 1/5 = 20%, 미확인 1/5 = 20%. 셋을 합쳐야 5건을 설명한다.
- unknown → 성공으로 치면 완료율이 부풀고, 실패로 치면 원인을 잃는다. 수집 지연 · 중단 · 취소 · 기록 누락을 확인한다.
- unknown을 빼고 1/4로 계산하면 질문 자체가 달라진다.

**p50과 p95**

```python
times = sorted(r["latency_ms"] for r in finished if r.get("latency_ms") is not None)
"p50_ms": median(times) if times else None,
"p95_ms": times[ceil(0.95 * len(times)) - 1] if times else None,
```

- 100, 200, 900 → p50 = 200, p95 위치 = 올림(0.95 × 3) − 1 = 2 → 900.
- **표본 3건이면 p95 = 최댓값.** 최댓값이 아니게 되려면 완료 20건부터. 이걸 SLA로 해석하지 않는다.
- 지연값이 없는 요청을 0ms로 채우지 않는다.

**0과 None은 다르다**

| 값 | 뜻 | 처리 |
| --- | --- | --- |
| 0 | 확인된 무료 | 합계에 0으로 포함 |
| None | 아직 모름 | 파악률을 낮추고 합계를 확정하지 않음 |

- 결과: `known_cost_usd=0.004`, `cost_coverage=0.6`, `total_cost_usd=None`.
- `None`은 계산을 빠뜨린 게 아니라 "전체 합계를 확정할 근거가 없다"는 표시.
- 알려진 비용 평균으로 확대 추정하면, 누락이 무작위라는 근거가 없는 한 편향된다.
- result_01.json의 `simulation: true` → 모의 자료임을 표시해 실제 운영 값으로 오해하지 않게 한다.

**퀴즈 3-1 — p95가 좋아진 장애**

- 장애로 느린 요청이 timeout되면 지연값이 사라져 p95가 900 → 200으로 **좋아져 보인다.**
- timeout은 failed가 아니라 오류율도 0, 미확인만 2건 늘어난다.
- 완료율(18/20) 하락을 함께 봐야 장애와 실제 개선을 구분할 수 있다.

## 3-2 토큰과 지연 측정

**상황:** 규정 한 문장으로 답할 질문인데 무관한 설명이 길게 들어간다.

**바꾸는 것은 하나뿐**

| 항목 | before | after |
| --- | --- | --- |
| 질문 · 근거 | 동일 | 동일 |
| 필수 사실 | 2만원 · 영수증 | 동일 |
| "회사 정원에는 나무가 있습니다." | 60회 | 없음 |

- 질문마다 before/after를 **번갈아** 실행해 시간 순서 효과를 줄인다.
- `row["cost_usd"] = None` — 임의 단가를 끼워 확정 비용처럼 표시하지 않는다. 서버 비용은 3-4에서 읽는다.
- 압축 알고리즘 평가가 아니라 불필요한 입력의 영향을 보는 작은 통제 사례다. 중요한 조건을 지우면 토큰이 줄어도 개선이 아니다.

**실제 실행 결과**

| 질문 | 버전 | 입력 토큰 | 출력 토큰 | 지연 ms |
| --- | --- | --- | --- | --- |
| q1 | before | 858 | 26 | 1733.0 |
| q1 | after | 138 | 26 | 1175.2 |
| q2 | before | 860 | 23 | 1302.8 |
| q2 | after | 140 | 22 | 1162.8 |

- 입력은 두 질문 모두 −720토큰, 출력은 거의 같다 → 줄어든 것은 **입력**.
- 지연은 q1 −557.8ms, q2 −140.0ms로 **토큰에 비례하지 않는다.**
- 토큰은 글자 수 추정이 아니라 `usage_metadata`의 실제 값. 없으면 None 유지.
- 입력과 출력을 나눠야 "입력을 줄였는데 답변이 길어진" 상황도 구분된다.

**어느 구간의 시간인가**

| 값 | 범위 |
| --- | --- |
| latency_ms | answer()의 perf_counter 구간: 검색 + 입력 구성 + 네트워크 + 모델 대기 (로컬) |
| ChatOpenAI 시간 | 모델 호출 구간만 (Langfuse 서버 표시) |

- `flush()`는 측정 뒤에 실행돼 latency_ms에 포함되지 않는다.
- 어느 시간을 쟀는지 밝히지 않으면 서로 다른 값으로 개선률을 계산하게 된다.

**적은 표본은 원인 탐색용 증거**

1. 입력 토큰이 줄었는가
2. 답변의 사실과 출처가 유지됐는가
3. 지연은 더 많은 표본으로 확인

- 버전당 2건 → 통계적 성능 향상이라고 말하지 않는다.
- after가 더 느려도 숨기거나, 빠르게 나올 때까지 반복해서 고르면 안 된다.

**퀴즈 3-2 — "전체 규정을 다 넣자"**

- all_docs 버전은 입력 토큰이 늘고, q1 출처가 meal 하나에서 세 문서로 늘어난다.
- q2(규정 밖 질문)는 검색 결과가 비었는데 답변에 출처가 붙는다 → `document_ids`만 보면 놓친다. **답변 문장의 대괄호**를 봐야 한다.

## 3-3 오류율과 사용자 피드백

**상황:** API 호출은 모두 성공했는데 사용자는 만족하지 않는다.

| 신호 | 보는 것 | 한계 |
| --- | --- | --- |
| 기술적 오류율 | failed / 전체 요청. 실행이 기술적으로 끝났는가 | 자연스러운 오답은 못 잡음 |
| 사용자 피드백 | 답이 업무에 도움이 됐는가 | 응답한 사람만 반영 |

- 네 건 모두 완료 + 한 답변이 너무 김 → 불만이 있어도 오류율 0%.
- 서버 오류 한 번 → 나머지 답변은 도움이 됐을 수 있다.
- 둘을 합쳐 하나의 성공률로 만들면 원인이 흐려진다.

**피드백은 trace_id에 연결**

```python
lf.create_score(trace_id=row["trace_id"], name="demo_feedback",
                value=value, data_type="BOOLEAN",
                comment="수업용 모의 피드백: " + reason)
```

- 질문 문장이 아니라 **사용자가 실제로 본 답변의 Trace**에 붙인다. 같은 질문으로 새로 만든 Trace에 붙이면 다른 실행을 평가하게 된다.
- 이 점수는 Trace 전체에 붙는다 (2장 평가 점수는 task observation에 붙었다).
- 다시 실행하면 같은 이름의 점수가 추가될 수 있다 → 운영에서는 피드백 ID로 중복 관리.
- False를 실제 사용자 불만이나 객관적 품질 실패로 단정하지 않는다.

**응답률 ≠ 긍정 비율**

| 기호 | 뜻 | 값 |
| --- | --- | --- |
| N | 전체 요청 수 | 4 |
| R | 피드백이 있는 요청 수 | 2 |
| P | 긍정 피드백 수 | 1 |
| 응답률 | R / N | 50% |
| 응답자 긍정 비율 | P / R | 50% |

- 두 값이 우연히 같아도 같은 지표가 아니다.
- 미응답을 긍정으로 넣으면 3/4처럼 보이지만 실제로 받은 긍정은 1건.
- 피드백을 남기는 사람은 매우 만족하거나 불만이 큰 쪽으로 치우칠 수 있다 → 전체 만족도로 확대하지 않는다.
- 피드백이 전혀 없으면 0%나 100%가 아니라 **미확인**.

**낮은 점수 → 평가 데이터 (2장으로 돌아가는 순환)**

낮은 점수 → Trace 열기 → 원인 분류(내용 · 출처 · 지연) → 익명화 → dev에 추가 → 2장 회귀 검사

| 피드백 | 먼저 볼 실행 증거 | 추가할 평가 사례 |
| --- | --- | --- |
| 증빙 안내가 빠졌어요 | 검색 문서와 모델 입력 | 영수증과 수료증 동시 포함 |
| 너무 길어요 | 필수 사실과 반복 문장 | 필수 조건 유지와 간결성 |
| 답변이 늦어요 | 전체 요청과 GENERATION 지연 | 같은 질문의 지연과 답변 품질 |

- 원문 피드백을 그대로 평가 데이터나 Cloud에 복사하지 않는다 (개인정보, 4장).
- "너무 길어요"에 글자 수만 줄이면 조건이 빠진 짧은 오답을 고를 수 있다. 필수 사실을 먼저 정한다.
- 부정 의견만 모으지 말고 정상 사례도 유지해야 과도한 방어와 품질 저하가 보인다.

**퀴즈 3-3 — 중복 클릭 피드백**

- rows에 없는 Trace(지난주 것)의 클릭은 건너뛴다.
- `score_id = f'{trace_id}-{user}'` → 더블 클릭은 한 표로, 마음을 바꾸면 마지막 값으로 덮어쓴다. 한 답변에 두 사람은 두 표.
- 응답률은 클릭 수가 아니라 **점수가 있는 Trace 수 / 전체 요청 수**. 점수가 없으면 긍정 비율은 None.
- score_id를 trace_id만으로 만들면 서로 다른 사람의 표가 하나로 합쳐진다.

## 3-4 개선 판단과 운영 대응

**상황:** 입력 토큰은 줄었지만 사용자 불만이 늘었다. 필요한 예외 조건까지 지운 압축이었다면 비용 절감만으로 변경을 유지할 수 없다.

**집계에서 개별 실행으로 내려간다**

1. 요청 수가 before = after인가
2. 같은 case_id의 토큰 · 지연 · 답변을 나란히
3. 차이가 큰 Trace의 근거와 생성 구간

- 먼저 같은 환경 · 기간 · app_version을 맞춘다. 다르면 변경 효과가 아니라 요청 구성 차이를 보게 된다.

**확인된 비용만 합산 (04_diagnose.py)**

```python
generations = [o for o in observations if o.type.upper() == "GENERATION"]
costs = [o.total_cost for o in generations]
row["cost_usd"] = (sum(costs) if costs and
    all(c is not None for c in costs) else None)
sleep(2.1)
```

- **GENERATION의 total_cost만** 모은다. 부모 span과 함께 더하면 중복된다.
- 하나라도 None이면 요청 전체 비용을 None으로. 일부만 더해 확정하지 않는다.
- 화면 상단의 `$0.00`은 반올림 표시일 뿐 무료가 아니다. 집계에는 반올림 전 서버 값($0.0002028 등)을 쓴다.
- `sleep(2.1)`은 무료 계정 조회 제한 간격이지 재시도 코드가 아니다.
- 서버 비용은 실제 청구서와 완전히 같은 회계 자료로 보장되지 않는다.

**실행 결과**

| 지표 | before | after |
| --- | --- | --- |
| requests | 2 | 2 |
| p50 ms | 1517.9 | 1169.0 |
| p95 ms | 1733.0 | 1175.2 |
| 비용 $ | 0.0004024 | 0.0001132 |
| 파악률 | 1.0 | 1.0 |

- 버전당 2건이라 p50은 두 값의 평균, p95는 큰 값.
- ChatOpenAI 행: before 약 1.72s · $0.000203, after 약 1.17s · $0.000059.
- 판정 **REVIEW** = 사람 검토 필요. decision은 코드에 고정된 값이고, 코드가 사실 정확성을 입증한 게 아니다.

**품질 조건을 같이 넣는다**

| 관측한 변화 | 바로 결론 내리면 안 되는 이유 | 다음 판단 |
| --- | --- | --- |
| 토큰 감소, 필수 증빙 누락 | 비용을 줄이며 품질을 잃음 | 후보를 보류하고 근거 복원 |
| 토큰 감소, 지연 증가 | 네트워크와 출력 길이 영향 가능 | 대표 질문으로 추가 측정 |
| 알려진 비용만 감소, 파악률 하락 | 미확인 비용이 늘어난 착시일 수 있음 | 수집과 가격 인식부터 확인 |
| 사실과 출처 유지, 토큰 감소 | 두 질문의 확인에 한정됨 | 더 넓은 평가와 운영 조건 검토 |

**경보는 행동으로 이어져야 한다**

- 경보 정의 = 지표 · 기간 · 임계값 · **최소 표본**. 최소 표본이 없으면 한 건이 느린 것과 계속 느린 것을 구분하지 못한다.
- SLO의 허용 실패량(error budget)을 얼마나 빨리 소모하는지(burn rate)도 볼 수 있다. 예: 99% 목표면 1%가 허용 실패량.
- 순서: 요청 수 · 미확인 비율 확인 → 영향 범위(기능 · 환경 · 버전) → 최근 변경 · 실패 Trace 대조 → 완화 · 복원 → 같은 사례로 재검증.

**복원할 때는 검증된 조합 전체를**

- 코드 · 프롬프트 버전 · 모델 설정 · 문서/색인 · 검색 설정을 함께 되돌린다 (2장 manifest와 연결).
- 프롬프트만 되돌려도 색인이나 모델이 바뀌었다면 이전 동작이 돌아오지 않을 수 있다.
- 규정이 정당하게 개정됐는데 옛 답변을 되살리면 올바른 복원이 아니다.
- 배포 명령 성공 ≠ 사고 해결 → 오류율과 사용자 기능을 다시 확인하고, 원인과 새 평가 사례를 남긴다.

**퀴즈 3-4 — 싸 보이는 후보 다시 판정**

- 후보 모델의 가격을 서버가 모르면 비용이 None → "싸졌다"가 아니라 **비용 미확인**.
- 판정 순서: 표본 부족 → 비용 미확인 → 비용 증가 → 유지 후보.
- 부모 span 비용(0.0009)까지 더하면 요청 비용이 부풀어 오른다.
