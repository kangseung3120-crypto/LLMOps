## 한 줄 요약

**프롬프트를 바꾼 뒤 "좋아졌다"고 말하려면, 같은 질문 · 같은 규칙으로 채점하고 평균이 아니라 질문별로 비교해야 한다.**

## 2-1 Golden Dataset

**정답 문장 대신 "답이 해야 할 행동"을 적는다.** LLM은 같은 뜻도 매번 다르게 말해서, 문장을 통째로 비교하면 맞는 답도 틀린다.

| 필드 | 뜻 | 예 (d01 식비) |
| --- | --- | --- |
| terms | 답에 꼭 있어야 할 표현 | 2만원, 영수증 |
| citations | 답에 붙어야 할 출처 ID 집합 | meal |
| abstain | "확인할 수 없습니다"로 보류해야 하나 | false |

- 질문 6개 = dev 4(정상 2 · 경계 1 · 보류 1) + holdout 2. 잘되는 질문만 모은 시연 목록이 아니라 서로 다른 실패를 담는다.
- **dev**는 결과를 보며 프롬프트를 고치는 용도, **holdout**은 후보를 고른 뒤 한 번만 보는 용도. holdout을 보고 또 고치면 그것도 사실상 dev가 된다.
- 보류 질문의 빈 배열은 누락이 아니라 "요구하지 않음". 대신 abstain=true로 보류 행동을 요구한다.

**01_dataset.py main()** — 한 질문을 세 칸으로 나눠 등록한다.

| 칸 | 내용 | 누가 쓰나 |
| --- | --- | --- |
| input | id, question | Task(모델). id는 비교용 키 |
| expected_output | terms, citations, abstain | Evaluator만. 모델은 못 봄 |
| metadata | split, kind | 사람이 화면에서 구분 |

- dev와 holdout을 **별개 데이터셋**으로 만든다. new_name으로 실행마다 새 이름이라 이전 것을 덮어쓰지 않는다.
- description("수업용 가상 규정 QA / dev")은 화면용 메모일 뿐, 채점에 영향 없음.

**validate()** — 등록 전에 채점표 자체를 검사한다.

1. ID 중복 금지 — 두 실험을 잇는 키라서
2. split은 dev/holdout만 — 오타면 어느 데이터셋에도 안 들어가고 조용히 사라진다
3. expected 키 세 개 정확히 + abstain은 진짜 bool — 문자열 "false"는 참으로 취급된다
4. citations ⊆ 실제 문서 ID — 모델 출력에 맞춰 출처를 추가하지 않는다
5. abstain이면 terms · citations는 비어야 함 — 동시에 만족할 답이 없는 충돌

등록 성공 = 채점표를 준비했다는 뜻일 뿐, 모델 성능과는 아직 무관하다.

## 2-2 프롬프트 버전 고정

**프롬프트만 바꾸고 나머지는 고정한다.** 모델과 검색 개수까지 같이 바꾸면 무엇 덕분에 좋아졌는지 설명할 수 없다.

| 고정 | 바꿈 |
| --- | --- |
| 질문 · 문서 · 검색 · 모델 · 평가기 | 프롬프트만 (v1 기준선 → v2 후보 POLICY) |

- 프롬프트는 **버전 번호**로 불러온다. `latest` · `production` 라벨은 누가 새 버전을 등록하면 가리키는 대상이 바뀐다 (퀴즈 2-2: 팀원 등록 후 latest는 v3).
- 같은 이름으로 create_prompt를 두 번 하면 v1, v2가 생기고, 반환된 version을 result_02.json에 저장해 다음 단계가 쓴다.
- 함정: 출처를 붙이라는 지시가 보류 답에도 복사돼 **"확인할 수 없습니다. [meal]"**이 나올 수 있다. 지시문이 있다고 모델이 지킨 건 아니고, 실제 응답으로 확인해야 한다.
- 프롬프트 버전만 같아도 문서 · 평가규칙 · 모델이 바뀌면 다른 비교다. 그래서 데이터 해시 · 평가기 해시 · 모델명 · 프롬프트 버전을 결과 파일에 함께 남긴다.

## 2-3 Python 평가 — evaluate()

**Task는 답을 만들고(모델 호출), Evaluator는 내 PC의 Python 함수로 검사한다.** 점수를 네 개로 나눠야 무엇이 부족한지 보인다.

| 점수 | 기준 | 통과해도 못 잡는 것 |
| --- | --- | --- |
| required_terms | 필수 표현 모두 포함 | "2만원이 아닙니다"도 통과 |
| citation_match | 대괄호 출처 집합이 기대와 **정확히 같음** | 문장이 그 근거를 지지하는지 |
| answer_behavior | "확인할수없" 여부 = abstain | 같은 뜻의 다른 보류 표현 |
| rule_pass | 위 셋 모두 통과 | 의미 정확성 전체 |

- 정규화는 공백 · 쉼표 제거뿐: "2만 원" → "2만원", "20,000" → "20000". 그래서 보류 검사 문자열도 띄어쓰기 없는 "확인할수없".
- 출처는 포함이 아니라 집합 비교: [meal][travel]처럼 출처를 더 붙여도 실패, 중복 [meal][meal]은 통과.
- 보류 질문은 terms가 []이고 all([])은 True라서 required_terms는 자동 통과, 실제 판단은 출처 · 보류 검사가 한다.
- 두 버전에 같은 평가기를 쓴다. 평가기를 바꾸면 기준선 · 후보를 둘 다 다시 채점해야 공정하다.

**오류 ≠ 0점**

- 출처가 틀린 완료 답 = 정상 채점된 0점 → 비교에 포함
- API 실패 · 미완료 = 채점할 답이 없음 → evaluate()가 ValueError, 0점으로 채우지 않는다
- SDK는 Task가 실패한 행을 결과에서 **빼 버린다** → 데이터셋 ID 집합 − 결과 ID 집합으로 missing을 찾는다 (퀴즈 2-3)

실제 실행 d03: 기준선은 서류 두 개는 답했지만 [training]이 없어 citation_match False, 후보는 네 점수 모두 통과.

## 2-4 회귀 판정 — compare()

**평균이 올라도 한 질문이라도 나빠지면 BLOCK이고, 끝까지 통과해도 결론은 자동 배포가 아닌 REVIEW다.**

```
dev 결과를 질문 ID로 짝짓기
  ↓
ID 4개 · 중복 없음 · 양쪽 같음? ── 아니오 → ValueError · 비교 불가
  ↓
오류 · 점수 누락 없음? ─────────── 아니오 → BLOCK · 평가 실패
  ↓
후보 4건 통과 + 악화 없음? ─────── 아니오 → BLOCK · 회귀 (모델 추가 호출 0회)
  ↓ CHECK_HOLDOUT → 모델 2회 호출
holdout 2건 모두 통과? ─────────── 아니오 → BLOCK · holdout 실패
  ↓
REVIEW (사람 검토, 자동 배포 아님)
```

- 결과를 `{id: 행}` 딕셔너리로 바꿔 **같은 ID끼리** 비교한다. Langfuse가 돌려주는 순서는 다를 수 있어서 zip으로 묶으면 d01과 d04를 비교하게 된다.
- delta = 후보 rule_pass − 기준선 rule_pass, 질문마다 +1 / 0 / −1.
- 수업 기준: 후보 dev 4건 모두 통과 **그리고** 악화 없음 → CHECK_HOLDOUT.
- 예시: 평균 50% → 75%로 올랐어도 d04가 1 → 0이면 BLOCK.

**ID 검사가 세 개인 이유** — 각자 다른 사고를 잡는다.

| 상황 | 원본 행 수 | 딕셔너리 크기 | 잡는 검사 |
| --- | --- | --- | --- |
| SDK가 실패 행을 뺌 | 3 | 3 | 행 수 != 4 |
| 같은 ID 두 번 | 4 | 3 | 딕셔너리 크기 != 4 |
| 양쪽 ID가 다름 | 4 | 4 | set(before) != set(after) |

- 이 경우는 비교 자체가 불가능 → raise. 빠진 항목을 0으로 채우지 않는다.
- 행은 다 있는데 error나 점수 누락이 있으면 판정 BLOCK으로 남긴다.

**main()의 holdout 단계**

- CHECK_HOLDOUT일 때만 연결하고 모델 2회 호출. BLOCK이면 0회.
- 프롬프트는 03에서 평가한 **후보 버전 번호**로 다시 읽는다 (cache_ttl_seconds=0).
- holdout 2건이 모두 있고 오류 없이 rule_pass 1이면 REVIEW, 아니면 BLOCK. holdout은 dev 점수와 합치지 않는다.

실제 실행: rule_pass 25% → 100% (+75%p, 개선 3 · 악화 0) → CHECK_HOLDOUT → holdout 통과 → **REVIEW**.
